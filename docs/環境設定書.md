## 2. DNSとURL

### 2.1 DNS（2026-10-13の観測結果）

| レコード | 参照先 | 用途 |
| --- | --- | --- |
| `preview.good-space.jp` A | `210.131.218.235` | **新しいプレビューサイトのみ** |
| `good-space.jp` A（当時） | `34.111.141.225` | 既存の公開サイト。変更禁止 |
| 権威DNS | `ns1.xserver.jp` ～ `ns5.xserver.jp` | Xserver側で管理 |
| プレビューAのTTL（当時） | `3600` 秒 | DNS画面で確認 |

DNSの作業は原則Xserverの該当ドメイン管理側で実施。VPSの独立したDNS画面にレコードを作るだけでは、既存の権威DNSに反映されない場合がある。

```bash
# 確認のみ
dig +short NS good-space.jp
dig +short A preview.good-space.jp @ns1.xserver.jp
```

**禁止事項:** 正式な移行承認前に `good-space.jp`、`www.good-space.jp`、MX/SPF/DKIM/DMARC、既存サービスのサブドメイン設定を変更しない。

### 2.2 HTTPS/Nginx

| 項目 | 設定・格納先 |
| --- | --- |
| Nginxのプレビュー用ファイル | `/etc/nginx/sites-available/preview-good-space` |
| Nginxの有効化リンク | `/etc/nginx/sites-enabled/preview-good-space` |
| TLS公開名 | `preview.good-space.jp` |
| 証明書 | `/etc/letsencrypt/live/preview.good-space.jp/fullchain.pem` |
| 秘密鍵ファイル | `/etc/letsencrypt/live/preview.good-space.jp/privkey.pem` |
| 証明書管理 | Certbot（2026-10-13に4.0.0を確認） |
| ACME webroot | `/var/www/letsencrypt` |
| リバースプロキシ先 | `http://127.0.0.1:8080` |
| 観測時の証明書有効期限 | 2027-01-11（更新により変わる） |
| プレビュー検索エンジン | Nginxの `X-Robots-Tag: noindex, nofollow, noarchive` を追加した構成 |
| WordPress検索エンジン設定 | `blog_public = 0`（開発中） |

NginxのProxyヘッダーは原則 `Host`、`X-Real-IP`、`X-Forwarded-For`、`X-Forwarded-Proto`、`X-Forwarded-Host` を転送する。ホストのポート80はHTTPSへ転送し、ACME検証パスは証明書更新のためHTTPで到達可能にする。

**重要:** WordPressコンテナが`X-Forwarded-Proto: https`を理解するPHP設定が必要。**GitHubの`docker-compose.yml`には、このVPSで手動追加したHTTPS検知設定がまだ入っていない**。現行VPSの `docker-compose.yml` をGitHub版で一括上書きしない。2026-10-13には `$_SERVER` をComposeが置換してHTTP 500になり、`$$_SERVER` とエスケープすることで回復した経緯がある。

```bash
# 確認のみ
sudo nginx -t
curl -sSI https://preview.good-space.jp/ | head -n 15
sudo certbot certificates
systemctl list-timers --all | grep -i certbot || true
```

ブラウザが「保護されていない通信」を示す場合、証明書の検証結果・混在コンテンツ・HTTPリンク・リダイレクト・管理ページの表示先を確認する。HTTP 200だけでTLS安全性を保証したことにはならない。

## 3. Docker Compose設定

### 3.1 サービスと永続データ

| サービス名 | イメージ | コンテナ内待受 / 公開 |
| --- | --- | --- |
| `db` | `mariadb:11.4` | 3306/TCP（Docker内のみ、ホスト公開なし） |
| `wordpress` | `wordpress:php8.3-apache` | 80/TCP → `127.0.0.1:${WP_LOCAL_PORT:-8080}` |
| `wpcli` | `wordpress:cli-php8.3` | メンテナンス時のみ、`maintenance` profile |

永続ボリューム `db_data`（MariaDB）と `wp_data`（WordPress本体・uploads）。テーマとプラグインのソースはホストの `./frontend/` を読取専用でコンテナにマウントする。

```bash
cd /srv/goodspace-main
docker compose ps
docker compose config -q
docker compose --profile maintenance run --rm -T wpcli wp core version
docker compose --profile maintenance run --rm -T wpcli wp option get home
docker compose --profile maintenance run --rm -T wpcli wp option get siteurl
docker compose --profile maintenance run --rm -T wpcli wp option get timezone_string
```

更新前はコンテナの状態・ディスク容量・メモリを確認する。既存の別プロジェクトに影響が出る操作は避ける。

| 変数名 | 用途 | 設定値・確認方法 |

- VPS管理者・WordPress管理者・OpenRouterの認証情報は**それぞれ異なる**。平文パスワードをこの文書に転載しない。

## 5. AIブログ設定

### 5.1 設定画面・API

- 管理画面：`/wp-admin/admin.php?page=gsai-editor`
- API事業者：OpenRouter（OpenAI APIキーは互換ではない）
- APIエンドポイント：`https://openrouter.ai/api/v1/chat/completions`
- WordPress設定キー：`gsai_openrouter_key`、`gsai_openrouter_model`、`gsai_daily_enabled`
- 2026-10-13の画面のモデルID：`openai/gpt-4o-mini`。料金/提供可否はOpenRouter側で変更される。
- APIキーはWordPress DBに格納。GitHub・ログ・スクリーンショット・チャットへ実値を出さない。
- 「毎日07:00ごろに記事を自動公開」はWordPress設定 `gsai_daily_enabled=1` のとき有効。

```bash
# キーを出さず、設定と状態だけを確認
cd /srv/goodspace-main
docker compose --profile maintenance run --rm -T wpcli wp option get gsai_daily_enabled
docker compose --profile maintenance run --rm -T wpcli wp option get gsai_openrouter_model
docker compose --profile maintenance run --rm -T wpcli wp gsai status
```

APIキーが保存済みでも有効とは限らない。認証失敗401、残高・課金制限、HTTP 429、モデル応答不正などを確認する。テストは記事の誤公開を避けて計画的に実施する。

### 5.2 テーマ・記事のカテゴリー

`AI記事テーマ` は `gs_ai_topic` として保存。個別登録時にカテゴリーを選べる。未指定の場合は記事テーマ等のキーワードで8カテゴリから推定する。候補の14日分補充は `wp gsai refill`、毎日の公開処理は `wp gsai daily`。

```bash
docker compose --profile maintenance run --rm -T wpcli wp gsai refill
docker compose --profile maintenance run --rm -T wpcli wp gsai status
```

**注意:** 現行の日次処理は「**その日に公開済みの記事が1本でもあるなら追加しない**」方式。毎日AI記事1本を人の投稿とは別枠で保証する仕様ではない。API生成失敗時に運営チェックノートを自動公開することがあるため、内容を事後レビューする。

## 6. 定期実行・Cron設定

### 6.1 VPSで確認された構成

| 処理 | JSTの実行時刻 | 内容 |
| --- | --- | --- |
| WordPress Cron | 07:00を目標（アクセス依存） | `gsai_generate_one_draft` イベント。名称は旧仕様のまま |
| OS cron / テーマ補充 | 00:15 | 14日先までの記事テーマを補充 |
| OS cron / 記事公開チェック | 07:05 / 07:20 / 07:35 / 07:50 | 当日公開済みなら何もしない |
| OS cron / 同日再確認 | 08:05～23:05の毎時 | 未投稿なら再生成・公開を試行 |

スケジュール設定の正本：`scripts/install_daily_schedule.sh`。ホストに配置する実行コマンド：`/usr/local/sbin/goodspace-ai-daily`。Cron定義：`/etc/cron.d/goodspace-ai-daily`。ログ：`/var/log/goodspace/daily-publish.log`。ログローテーション：`/etc/logrotate.d/goodspace-ai-daily`（14世代）。

```cron
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
15 0 * * * root /usr/local/sbin/goodspace-ai-daily refill
5,20,35,50 7 * * * root /usr/local/sbin/goodspace-ai-daily
5 8-23 * * * root /usr/local/sbin/goodspace-ai-daily
```

**2026-10-13には日次公開Cron登録と`already_published`が利用者ログで確認された。0:15の補充Cronおよび新カテゴリー機能が現行VPSに反映済みかは、本書作成時点では再検証していない。**

```bash
# VPSの現在状態を調べる（確認のみ）
date +'%F %T %Z'
systemctl is-active cron
cat /etc/cron.d/goodspace-ai-daily
tail -n 50 /var/log/goodspace/daily-publish.log
docker compose --profile maintenance run --rm -T wpcli wp cron event list --fields=hook,next_run,recurrence
```

## 7. ソース更新と安全なリリース手順

**絶対に** `git reset --hard` でVPS全体を戻したり、`docker compose down -v` でDBを消去したりしない。

```bash
cd /srv/goodspace-main

# 1. データバックアップ
bash scripts/backup_local.sh

# 2. Git状態とVPS固有の差分を確認
git status --short
git fetch origin main
git diff -- docker-compose.yml
git diff HEAD..origin/main -- frontend/themes/goodspace frontend/plugins/goodspace-ai-editor

# 3. ソースファイルを個別バックアップ
mkdir -p /root/goodspace-release-backup
cp -a frontend/themes/goodspace frontend/plugins/goodspace-ai-editor /root/goodspace-release-backup/

# 4. テーマ・プラグインのみ更新（docker-compose.yml/.env/Nginxは対象外）
git restore --source=origin/main --worktree --   frontend/themes/goodspace frontend/plugins/goodspace-ai-editor

# 5. PHP構文確認
docker compose exec -T wordpress php -l /var/www/html/wp-content/themes/goodspace/functions.php
docker compose exec -T wordpress php -l /var/www/html/wp-content/themes/goodspace/inc/blog-categories.php
docker compose exec -T wordpress php -l /var/www/html/wp-content/plugins/goodspace-ai-editor/goodspace-ai-editor.php
docker compose exec -T wordpress php -l /var/www/html/wp-content/plugins/goodspace-ai-editor/goodspace-daily-publisher.php
```

PHPの構文に異常があれば公開URLをテストする前にバックアップから対象のテーマ/プラグインだけを復元する。**既存のWordPressデータと別サービスは操作しない**。

### 7.1 既存の未分類記事をカテゴリーに分類（任意）

事前にDBバックアップを取得する。すでに人が手動分類した投稿のカテゴリーは維持する。

```bash
cd /srv/goodspace-main
git restore --source=origin/main --worktree -- scripts/assign_blog_categories.php
docker compose --profile maintenance run --rm -T   -v "$PWD/scripts:/tmp/goodspace-scripts:ro"   wpcli wp eval-file /tmp/goodspace-scripts/assign_blog_categories.php
```

### 7.2 反映確認

```bash
curl -sS -L -o /dev/null -w 'HTTP %{http_code}, URL %{url_effective}\n'   https://preview.good-space.jp/
curl -sS -L -o /dev/null -w 'HTTP %{http_code}, URL %{url_effective}\n'   https://preview.good-space.jp/blog/
```

## 8. バックアップ・復旧設定

- `scripts/backup_local.sh` は `backups/<日時>/database.sql`、`uploads.tar.gz`、`checksums.sha256` を生成する。
- パスワード・個人情報を含むデータは `0600` 相当の権限制御で保護する。
- バックアップの**別ストレージへの転送、暗号化、世代管理、復旧テストは別途実施**。現状のスクリプトには未実装。
- 本番移行時は旧サイトも別途バックアップし、DNS/サイト復元のロールバック計画を作る。
- バックアップ確認のために実データや秘密情報をチャット・GitHubへ貼らない。

## 9. 障害時の切り分け

| 症状 | 第一確認箇所 | 初動 |
| --- | --- | --- |
| 404 / Nginx画面 | `server_name`、対象DNS、Nginxのサイト設定 | `nginx -t`。既存サイトの設定は上書きしない |
| HTTP 500 | WordPressコンテナログ、PHPの `$_SERVER` / Compose変数展開 | `docker compose logs --tail=100 wordpress` |
| HTTP 301繰返し | WordPress `home/siteurl`、`X-Forwarded-Proto` | TLS・プロキシ設定の整合 |
| DB起動失敗 | `docker compose ps`、dbログ、ディスク空き | ボリューム削除厳禁 |
| AI生成401 | OpenRouterキーの種類・期限 | キー文字列はログに出さない |
| AI生成429等 | OpenRouter側残高/制限、モデルID | 利用状況を確認 |
| AIの無投稿 | `gsai_daily_enabled`、Cron、公開済み件数、ログ | `wp gsai status` で最終結果を確認 |
| 分類されない記事 | カテゴリー存在、手動指定、テーマのバージョン | 新しい分類ルールと既存未分類を点検 |
| SSL警告 | 証明書・リダイレクト・混在コンテンツ | 証明書/ブラウザで詳細を検査 |
| ディスク逼迫 | `df -h`、Docker使用量 | 稼働中コンテナ/ボリュームの無差別削除禁止 |

## 10. 運用チェックリスト

**日次:** 直近の日付に公開記事があるか、カテゴリーは正しいか、AIの事実誤認がないか、cron失敗ログを確認。

**週次:** WordPress管理画面・OpenRouterの利用状況、証明書の更新見込み、検索UIとスマホ表示、リソースの空き容量、バックアップ成功を確認。

**月次:** 旧サイトとの差分、サービス内容・会社情報、写真、プライバシーポリシー、カテゴリの重複・記事品質、バックアップ復元手順、管理者アカウントを確認。

**本番移行判定:** サイトオーナーから明示の承認を受けるまで、`good-space.jp` のDNS・本番サイト・関連サブドメインを変更しない。
